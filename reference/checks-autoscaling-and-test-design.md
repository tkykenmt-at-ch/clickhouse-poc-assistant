# Checks: autoscaling and test design

Each check names the columns it reads, the rule, and the public source of the rule. The URLs have been checked; cite them as they are.

## Why autoscaling did or did not react

- **Columns**: `cpu_limit_cores` over the window (`queries/loadtest/31_window_cpu_10s.sql`), `uptime_seconds` (`queries/01_service.sql`), the service entry from the `get_services_list` tool.
- **Rule**: explain only from these sources, not from guesses. The documentation gives the CPU band: target utilization 53%, scale up above 75% and scale down below 37.5% of the allocated CPU, with the recommended size = peak CPU usage ÷ 0.53. CPU is smoothed with a 10-minute rolling median per replica, which is described only in the ClickHouse blog, so cite it as the blog (section "Smoothing out transient spikes"). Memory also drives the size: the recommender adds headroom to peak memory usage, and after query or replica OOMs it applies a 1.5x multiplier, so a run that hit `MEMORY_LIMIT_EXCEEDED` or an OOM can scale up even when CPU stayed in the band. Recommendations come from two lookback windows, 3 hours and 30 hours: the 30-hour window scales up in one step to the peak it saw, and the 3-hour window lets the size come down, so a size reached during a test can stay for hours afterwards. A reactive path can also scale up within seconds when a service clearly needs it (ClickHouse blog). Scaling is make-before-break. A step much shorter than 10 minutes moves the 10-minute median little. Vertical autoscaling applies to Scale tier services and Enterprise services with standard `1:4` profiles; Basic tier services stay at a fixed size, so ask for the tier before explaining why nothing scaled. Before explaining, read the configured range: if a `get_services_list` tool is available, take the entry whose `id` is this service and read `minReplicaMemoryGb`, `maxReplicaMemoryGb`, `numReplicas` and `idleScaling`. If min equals max, the service has a fixed size and cannot scale vertically, whatever the CPU did; if `cpu_limit_cores` already equalled the maximum's CPU (memory ÷ 4 on standard `1:4` profiles), it could not scale further. `get_services_list` does not return the tier; take it from `organizationTier` in `get_organization_cost` if that tool is available (see "Cloud tools" in `reference/checks-cloud-service.md`), otherwise ask for it or point to the console. The autoscaler's decisions are not visible from system tables or this tool; say so and point to the console.
- **Source**: https://clickhouse.com/docs/products/cloud/features/autoscaling/scaling-recommendations , https://clickhouse.com/docs/products/cloud/features/autoscaling/vertical , https://clickhouse.com/blog/smarter-auto-scaling , https://clickhouse.com/blog/making-clickhouse-cloud-autoscaling-more-reactive (blog) , https://clickhouse.com/docs/products/cloud/features/autoscaling/make-before-break

## How to compare two runs

- **Columns**: `p50_ratio`, `p99_ratio`, `read_rows_ratio`, `avg_cpu_ms_a`/`_b`, `executions_a`/`_b`, `query_cache_read_share_a`/`_b`, `condition_cache_hit_share_a`/`_b`, `fs_cache_hit_rate_a`/`_b`, `avg_peak_threads_a`/`_b`, `errors_a`/`_b` (`queries/loadtest/32_compare_windows.sql`).
- **Rule**: a comparison is fair only when the two runs had the same load, the same cache conditions and one change between them. If `query_cache_read_share`, `condition_cache_hit_share` or `fs_cache_hit_rate` differs between the runs, or the number of executions differs a lot under a closed-loop tool, say that the ratio mixes the change with that difference. A NULL `fs_cache_hit_rate` means the run read nothing through the filesystem cache, so that column tells nothing about fairness. If `30` shows inserts or other heavy patterns in only one of the windows, the runs did not have the same conditions. With few executions of short queries, p99 is set by one or two runs; say so. Change one thing at a time and use the median of repeated runs after warm-up. To find where the time went in each run, run `30` for both windows.
- **Rule (setting changes)**: when the change is a setting, compare its value in both runs with `Settings['<name>']` from `system.query_log`. If the value is the same in both runs, the setting did not change, and the runs compare nothing. On ClickHouse Cloud, `Settings` also holds values the service sets by default, so a key being present does not mean the client set it. For example, `max_threads` defaults to the vCPU count of a replica, so on a 2-vCPU service `max_threads = 2` changes nothing. To test a lower value, use one below the default (`getSetting('<name>')` shows the default for the connection). `avg_peak_threads` comes from `peak_threads_usage`, the peak number of threads linked to the query's thread group at the same time. That count is not limited to the `max_threads` processing threads, so it can be higher than `max_threads`; do not use it to judge whether `max_threads` applied.
- **Source**: https://clickhouse.com/docs/guides/clickhouse/performance-and-monitoring/isolate-query-bottlenecks , https://clickhouse.com/docs/reference/settings/session-settings/max-threads , https://github.com/ClickHouse/ClickHouse/blob/master/src/Interpreters/ThreadStatusExt.cpp (`ThreadGroup::linkThread` counts `peak_threads_usage`)

## How to run the next test

- **Rule**: fix the size (minimum = maximum) when measuring capacity; hold each step well beyond the 10-minute smoothing window when observing autoscaling; use an open-loop rate when the question is whether a rate can be sustained; tag each step with `log_comment` so `query_log` can be filtered by step; measure cold and warm runs separately and keep cache conditions the same between compared runs; before testing a setting, check its current value with `getSetting('<name>')` and choose a value that differs from it.
- **Source**: https://clickhouse.com/docs/products/cloud/features/autoscaling/vertical , https://clickhouse.com/docs/reference/settings/session-settings/log#log_comment , https://clickhouse.com/docs/guides/clickhouse/performance-and-monitoring/isolate-query-bottlenecks
